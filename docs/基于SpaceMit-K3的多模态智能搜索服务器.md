# 基于 SpacemiT K3 的多模态智能搜索服务器

> **一句话价值主张**：一句话描述，500ms 定位目标画面，百万级视频帧本地语义检索，数据零出境。

---

## 1. 产品定义

多模态智能搜索服务器是一种基于 SpacemiT K3 RISC-V 芯片集群的**视频内容语义检索系统**，支持文本、图片、视频等多种模态的输入查询，通过向量化和语义匹配技术，在海量视频监控数据中快速定位目标内容。

核心能力：
- **自然语言搜索**：用自然语言描述要找的内容，如"穿红色衣服的人在门口"
- **图片搜索**：上传图片，找到视频中相似的画面或目标
- **跨摄像头追踪**：在多个摄像头间追踪同一目标的轨迹
- **分布式并行检索**：查询并行分发到所有 Worker 节点，搜索速度随节点数线性提升
- **VLM 精排**：对初步检索结果使用视觉语言模型进行精确重排序

### 2.2 K3 芯片硬件能力

| 硬件单元 | 规格 | 在搜索服务器中的作用 |
|---------|------|---------------------|
| CPU | 8 核 RISC-V (RVV 1.0) | VLM 重排序、意图解析、余弦相似度计算 |
| NPU | 60TOPS INT4 | Chinese-CLIP 嵌入计算、YOLO 检测 (索引管线) |
| VPU | H.264/H.265 硬解码 | 视频流解码 (实时索引) |
| DDR | LPDDR5x 8GB | 向量索引缓存 (100万+ 向量) |
| 存储 | NVMe SSD | 向量数据库持久化 |
| 网络 | GbE | Hub ↔ Worker 通信 |
| 功耗 | 10-15W | 7×24 索引 + 搜索服务 |

### 2.3 数据流程

```
数据流 A: 实时索引 (后台持续运行)

  视频流 (RTSP)
       ↓
  K3 VPU 硬件解码
       ↓

       ├─ 目标裁剪 (人/车/物 区域)
       └─ 全帧场景
            ↓
  K3 NPU Chinese-CLIP 嵌入 (向量化)
       ├─ 目标向量 (512维)
       └─ 场景向量 (512维)
            ↓
  本地向量数据库 (SQLite + 向量索引)
       ├─ 向量数据
       ├─ 时间戳
       ├─ 摄像头 ID
       ├─ 目标类型 + 属性
       └─ 缩略图路径

  索引速率: 每 Worker 节点 ~5fps 持续索引
  存储增长: ~1MB/分钟 (向量 + 元数据)

数据流 B: 搜索查询 (用户触发)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  步骤 1: 意图解析
  ─────────────────
  用户输入: "昨天下午3点穿红衣服的人在北门"
       ↓
  Intent Parser (正则 + 规则):
  {
    "time_range": "2024-01-15 15:00 ~ 16:00",
    "target_type": "person",
    "attributes": {"color": "red"},
    "location": "north_gate",
    "cameras": ["cam-north-01", "cam-north-02"]
  }

  步骤 2: 查询向量化
  ─────────────────
  查询文本 "穿红衣服的人"
       ↓
  K3 NPU Chinese-CLIP 文本编码器
       ↓
  查询向量 (512维)

  步骤 3: 联邦搜索
  ─────────────────
  查询向量 + 过滤条件
       ↓ 并行分发
  Worker #1: 本地向量库 → 余弦相似度 → Top-50
  Worker #2: 本地向量库 → 余弦相似度 → Top-50
  Worker #N: 本地向量库 → 余弦相似度 → Top-50
       ↓
  Hub 聚合: N × Top-50 → 全局 Top-100

  步骤 4: VLM 重排序 (可选)
  ─────────────────
  Top-20 结果图片 + 原始查询
       ↓
  SpaceMIT推理引擎 Qwen3-VL-2B 逐一验证:
  "这张图片中是否有穿红色衣服的人？相关性评分？"
       ↓
  重排序后的最终结果

  步骤 5: 返回结果
  ─────────────────
  排序结果:
  [
    {缩略图, 时间, 摄像头, 相似度, VLM描述},
    ...
  ]
```

### 2.4 模块详细描述

#### 模块 A: 意图解析器 (Intent Parser)

| 属性 | 说明 |
|------|------|
| 输入 | 自然语言查询字符串 |
| 输出 | 结构化查询条件 (JSON) |
| 解析维度 | 时间范围、目标类型、颜色、行为、位置、摄像头 |
| 实现方式 | 正则规则 + 关键词匹配 (快速，<5ms) |
| 扩展 | 可选 VLM 辅助解析复杂查询 |
| 多语言 | 支持中文/英文自然语言输入 |

#### 模块 B: 联邦搜索引擎 (Federated Search)

| 属性 | 说明 |
|------|------|
| 架构 | Hub 分发 → Worker 本地搜索 → Hub 聚合 |
| 并发控制 | Semaphore 限制同时查询的 Worker 数 |
| 超时 | 单 Worker 查询超时 5s，超时跳过 |
| 聚合策略 | 全局 Top-K 排序 + 时间窗口去重 |
| 分数混合 | 向量相似度 × 0.7 + 时间衰减 × 0.2 + 属性匹配 × 0.1 |
| 层级搜索 | 中心 Hub → 区域 Hub → Worker (500+ 节点) |

#### 模块 C: 向量搜索引擎 (每个 Worker 本地)

| 属性 | 说明 |
|------|------|
| 向量维度 | 512 (Chinese-CLIP-ViT-B/16) |
| 索引方式 | SQLite + 暴力余弦相似度 (精确) |
| 单节点容量 | 100 万+ 向量 (~500MB 存储) |
| 搜索延迟 | <200ms (100 万向量 Top-100) |
| 索引更新 | 实时追加，无需重建 |
| 过滤 | 时间范围 + 摄像头 + 目标类型 预过滤 |

#### 模块 D: VLM 重排序器 (Reranker)

| 属性 | 说明 |
|------|------|
| 模型 | Qwen3-VL-2B (基于llama.cpp的SpaceMIT推理引擎) |
| 输入 | Top-K 结果图片 + 原始查询 |
| 输出 | 相关性分数 (0-1) + 解释文本 |
| 延迟 | 30-50s/张 × Top-20 |
| 触发条件 | 用户手动启用 / 高精度模式 |
| K3 加速 | 基于llama.cpp的SpaceMIT推理引擎 |

#### 模块 E: 实时索引管线 (每个 Worker)

| 属性 | 说明 |
|------|------|
| 输入 | RTSP 视频流 (1-4 路/Worker) |
| 处理链 | VPU 解码 → NPU YOLO → 裁剪 → NPU Chinese-CLIP → 存储 |
| 索引速率 | ~5fps 持续索引 |
| 存储增长 | ~1MB/分钟 (向量 + 元数据 + 缩略图) |
| 目标类型 | 人、车、动物、物品 (COCO 80类) |
| 属性提取 | 颜色直方图、尺寸、位置区域 |

## 3. 核心优势

### 3.1 K3 方案 vs 传统方案

| 维度 | 传统视频检索 | 云端 AI 搜索 | GPU AI 服务器 | K3 多模态搜索 |
|------|------------|------------|-------------|-------------|
| 搜索方式 | 时间+摄像头 | 文本/图片 | 文本/图片 | 文本/图片/组合 |
| 语义理解 | 无 | 有 | 有 | 有 (VLM 精排) |
| 数据位置 | 本地 | 云端 | 本地 | 本地 (边缘) |
| 隐私保护 | 好 | 差 | 好 | 好 |
| 硬件成本 | 低 | 按量付费 | 高 (5-20万) | 低 (~2000/节点) |
| 扩展性 | 差 | 好 | 中 | 好 (线性扩展) |
| 搜索延迟 | 慢 (逐帧) | 快 | 快 | 快 (<500ms) |
| 月度费用 | 无 | 有 | 无 | 无 |

### 3.2 客户痛点与解决方案

| 客户痛点 | K3 方案如何解决 |
|---------|---------------|
| 事后追溯需人工逐帧回看 | 自然语言搜索，500ms 返回结果 |
| 云端方案月费高且有隐私风险 | 一次购买，零月费，数据不出本地 |
| GPU 服务器成本高、功耗大 | 单节点 ~2000 元，10-15W 功耗 |
| 传统检索只能按时间/摄像头查找 | 支持语义搜索，描述画面内容即可定位 |
| 单点搜索无法覆盖大规模部署 | 分布式并行检索，500+ 节点线性扩展 |
| 搜索结果不精确，误报多 | VLM 精排验证，大幅提升准确率 |

### 3.3 K3 芯片核心技术优势

- **NPU Chinese-CLIP 加速**：K3 NPU 60TOPS 加速 Chinese-CLIP 嵌入计算，实时索引无延迟
- **分布式并行搜索**：N 个 Worker 并行检索，搜索速度随节点数线性提升
- **VLM 精排**：Qwen3-VL-2B + SpaceMIT推理引擎加速，对 Top-K 结果精确验证
- **边缘索引**：数据在 Worker 本地索引和存储，无需集中传输
- **层级扩展**：两级 Hub 架构支持 500+ 节点大规模部署
- **隐私合规**：所有数据本地存储和处理，满足数据安全法规

## 4. 应用场景

### 4.1 安防事后追溯

**部署规模**：4-8 个 K3 Worker 节点，16-32 路摄像头

**数据流**：
```
事件发生 → 用户输入描述 "凌晨2点北门附近的黑色轿车"
→ Intent Parser: {time:"02:00", location:"north", target:"car", color:"black"}
→ 查询向量化 (K3 NPU Chinese-CLIP)
→ 联邦搜索 (并行查询所有 Worker)
→ 结果聚合 Top-100 → VLM 精排 Top-20
→ 返回: 缩略图 + 时间 + 摄像头 + 相似度
→ 用户点击 → 跳转录像回放
```

**客户价值**：本地搜索 <500ms，无需上传视频到云端，隐私合规

### 4.2 连锁门店管理

**部署规模**：500+ 门店，每店 1-2 个 K3 Worker，区域 Hub + 中心 Hub

**数据流**：
```
中心管理平台 → 查询 "所有门店中未佩戴口罩的员工"
→ 中心 Hub → 区域 Hub (华东/华南/华北...)
→ 各区域 Worker 并行搜索
→ 区域 Hub 聚合 → 中心 Hub 全局排序
→ 返回: 门店+时间+截图 列表
```

**客户价值**：每店 1 个 K3 节点 (~2000元)，500 店总投入 ~100 万，替代百万级 GPU 方案

### 4.3 智慧城市

**部署规模**：16-32 个 K3 Worker 节点，64-128 路摄像头

**数据流**：
```
公安查询 → 上传嫌疑人照片 + "今天上午在地铁站附近"
→ CLIP 图片编码 (K3 NPU Chinese-CLIP)
→ 联邦搜索 (时间+位置过滤 + 向量匹配)
→ 跨摄像头轨迹追踪
→ 返回: 目标出现的时间线 + 轨迹地图
```

**客户价值**：路口边缘部署，数据不出辖区，满足公安数据安全要求

### 4.4 工业质检追溯

**部署规模**：4-8 个 K3 Worker 节点，8-32 路产线摄像头

**数据流**：
```
质检员发现缺陷 → 拍照上传 + "类似缺陷的产品"
→ Chinese-CLIP 图片编码 → 联邦搜索 (产线摄像头)
→ 返回: 相似缺陷出现的时间 + 工位 + 频率
→ 追溯分析: 缺陷集中在某工位/某时段
```

**客户价值**：产线现场部署，实时索引，缺陷发现后秒级追溯
